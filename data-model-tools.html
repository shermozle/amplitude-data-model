Scope: event, user, and persisted

  
Amplitude has two scopes and one mechanism that sits between them. Worth getting straight before you map anything across, because the third one is where most of the eVar behaviour ends up.


  
1 · The two scopes

  

    

      Event scope
      
Describes the thing that happened. It travels with the event and is never carried to the next one.

      
plan_tier on a plan selection, error_code on an error, search_term on a search.

    

    

      User scope
      
Describes the person. Set it once and it applies to every event afterwards until something changes it.

      
customer_segment, tenure_months, the plan they're currently on. It holds the current value, not the value at the time of any given event.

    

  


  

    

      
        

          Event
          Event scopepage_section
          User scopeaccount_id
        

      
      
    

  

  
The event property is present only where it was sent. The user property is empty until login, then applies to everything after it — including, from that point on, when you look back at this user's profile.


  
2 · Persisted properties

  
Some context belongs to the journey rather than to one event or to the person: which campaign brought someone in, which page started the session, which recommendation led to an item. A persisted property takes an event property and applies allocation and expiration rules to it, so the value reaches events that never carried it.


  

    

      Allocation
      
Which value sticks: the first one, the latest one, or the earliest and latest known — the last two of which apply backwards as well as forwards.

    

    

      Expiration
      
How long it keeps applying. End of session, or a custom window such as 7 or 30 days.

Three you'd configure

  
    
    
  • Entry page. page_path, Original, Session. Group purchases by where the session started, even though the purchase event never carried a page path.
    • 
    
  • Campaign across sessions. utm_campaign, Most recent, 7 days. Connects a marketing touch to a conversion days later without stamping UTMs on every event.
    • 
    
  • Item-level discovery. discovery_method, Most recent, Session, bound to products.item_id. Each item in a cart keeps the search, recommendation or promo that led to it, so revenue attributes per product rather than crediting the whole order to one source. This is the piece that needs the array from tab 06.
    • 
  


  

    Two limits worth knowing. Persisted properties are computed when you query, so they don't appear on the user profile and they aren't in raw exports — anyone reconciling a warehouse table against a chart needs to know that. They also read event properties only; a value that arrives only as a user property can't be an input, which is a reason to send marketing context as event properties as well.

    The difference that matters most. An eVar's expiry and allocation are applied when the hit is collected, so changing them only affects data from that point on. Three IDs

  
Two of them you send. The third Amplitude works out. Here are four events from one person on two devices, which is the whole mechanism in one table.


  

    
    
  


  

    

      
        

          Device ID you send
          User ID you send, once you know it
          Event
          Amplitude ID at the moment it arrived
        

      
      
    

  


  


  

    

      Device ID
      
Anonymous, minted by the SDK, one per browser or app install. Present on every event. If you send nothing else, this is who the event belongs to.

    

    

      User ID
      
Yours to define, and only present once you know who someone is. Whatever you decide a person is: a customer ID, an account ID, a resolved subscriber.

    

  

  

    Amplitude ID
    
Internal, and the one that actually gets counted. Nothing you send is called amplitude_id — it's derived from the pattern of device and user IDs arriving together, and it can change after the fact.

    The level above the person: the Accounts add-on
    
  
    Everything above resolves to an individual. Some questions aren't about individuals — how is this business customer tracking, how many households upgraded, which accounts have gone quiet. Amplitude reports on users by default; the Accounts add-on adds group-level analysis so charts can count and segment by account instead.
    

  
    
    
    
      What a group is
      
    A type and a value — account id: 4471, household: h_902. You define the types you need, and a user can belong to more than one.
    
      
    Group properties describe the account rather than the person: plan count, contract value, segment.
    
    
    
    
    
      What it changes
      
    Charts get a group option alongside users, so a funnel can count accounts that converted rather than people who clicked.
    
      
    Cohorts can be group-level too, and dynamic group properties can carry a KPI — active users in the last 7 days, say — onto each account.
    
    
    
  
    

  
    
    Worth deciding before instrumentation, not after. Group membership isn't applied to historical data, so events already ingested won't retrofit into a group type added later. It's also the natural home for the service-versus-person problem from the header enrichment scenario: the subscriber identifies a service, and the account is the thing several services hang off.

    Cohorts, and how they differ from segments
    
  
    Both tools have something called a segment, and they mean roughly the same thing. The word without a counterpart is cohort. Pick a question and compare how each side expresses it, and what you can then do with the result.
    

  
    
    
    
    
  
    

  
    
    
    
      Adobe
      
    
      
    
      
    
      
      
    
      
    
      
      Amplitude
      
      
      
      
      
      
      
        
    
        
  
        

  
        

  
        The three differences worth remembering
        
  
          
    
        • A cohort is a list of people, not a filter. Amplitude computes it, stores the membership and refreshes it on a schedule. An Adobe segment is a definition applied when a report runs. That's why a cohort can be sent somewhere and a segment generally can't.
          • 
    
        • There is no hit-scoped cohort. Adobe segments have hit, visit and visitor containers, which is the scope model again. A cohort is always a set of users; if you want hit-level filtering you do it on the chart.
          • 
    
        • Membership is addressable outside analytics. The same cohort filters a chart, targets an experiment, gates a guide, and syncs to an ad platform or CRM. In Adobe the analytics segment and the activation audience usually live in different products with different definitions, and reconciling the two is its own job.
          • 
  
        

  
        
    The one to watch. Because a cohort is computed and stored, a large one takes time to build and doesn't update the instant someone qualifies. For anything that needs to react within a session, an inline filter on the chart or a real-time behavioural target is the right tool, not a cohort.

        Arrays, and the end of s.products
        
  
        Adobe gives you one products variable with positional string syntax. In Amplitude any property can hold an array, and you can have several on the same event. Edit the string and both sides update.
        

  
  

  
        

  
        
    
        
      
        Adobe parsed positionally
        
      
        
    
        
    
        
      
        Amplitude one array property
        
      
        
    
        
  
        

  
        
    Six positions, counted by semicolon. Category, product, quantity, price, events, merchandising eVars, in that order, with empty slots held open by ;;. Miss one and the price lands in the events column.
  
        

  
        One products string, versus as many arrays as you want
        
  
        products isn't a special variable in Amplitude. It's an event property that holds an array, so nothing stops you having several on the same event.
        

  
        {
  "event_type": "Order Completed",
  "event_properties": {
    "products": [
      { "name": "Mobile Plan Premium", "price": 65.00, "order_type": "activation" },
      { "name": "Handset",             "price": 1849.00 }
    ],
    "promotions_applied": ["SPRING", "PORTIN_BONUS"],
    "components_seen":    ["hero_a", "plan_grid"],
    "add_ons":            ["static_ip", "wifi_booster"]
  }
}
        

  
        Adobe's answer for the second and third of those is list variables or a run of numbered context data keys — promo.0, promo.1, promo.2 and so on. It works, and it caps out wherever the numbering stopped.
        

  
        Before you model with them
        
  
          
    
        • Grouping by an array unnests it. Group a chart by products.name and you get one row per product, not one row per concatenated string.
          • 
    
        • A user can be counted under several values at once. An order containing two products appears under both. That suits product analysis and doesn't suit totals, so agree which metrics are order-level and which are line-level before anyone builds a dashboard.
          • 
    
        • Merchandising eVars become fields. The binding syntax, the conversion-versus-merchandising distinction and the binding events all go. A value bound to a product becomes a key on that product's object.
          • 
    
        • Arrays of objects and arrays of scalars are both fine. Line items want objects. A list of promotion codes or add-on names is happier as a plain array of strings.
          •

        Things that go away
        
  
        Common Adobe patterns and what happens to them. Each exists for a good reason: variables are a numbered, finite resource, so a lot of implementation craft goes into using them efficiently. When the resource stops being scarce, most of that craft stops being needed.
